## Terms and knowledge

As I continued my research, I came across several key terms and technologies that are crucial for making the QCAR simulation work. **Gazebo** is one of the most prominent tools I encountered. It is a powerful open-source robotics simulator used to create realistic 3D environments for testing robots. It supports physics engines and sensor models, which can be critical for simulating real-world behaviors, and I see it as a potential core component for the simulation. Moving on to **ROS** (Robot Operating System), I learned that it is not an operating system per se, but a flexible framework for writing robot software. It includes a collection of tools, libraries, and conventions for building complex robot behavior. I found that ROS is essential for handling the communication between various parts of the simulation, especially for managing sensor data, actuator commands, and overall system coordination.

In terms of connectivity, I’ve started to understand that ROS uses a publisher-subscriber model, where different nodes communicate by publishing messages on topics that other nodes can subscribe to. This model could be key for ensuring seamless interaction between the QCAR system and the virtual environment. I also looked into creating a **virtual environment** to host these simulations and manage the entire workflow. The idea is to create a containerized environment, using tools like Docker or virtual machines, that ensures a consistent and isolated setup for running these simulations without interfering with the host system.

As for QCAR’s connectivity, from my preliminary research, I’ve gathered that the connection involves both hardware and software layers. While I don’t have all the technical specifics yet, it appears to rely heavily on network communication between the physical or virtual device running QCAR and the programmer's machine. Understanding this interaction is essential to integrate the simulation properly and ensure that the **virtual machine**, **Gazebo**, and **QCAR** can all work in unison. At this stage, the main focus is on understanding these foundational concepts and how to ensure smooth connectivity between all components in the system.

In the context of **QCARs**, several key terms and technologies are essential for understanding how the system operates and interacts. **PID** (Proportional-Integral-Derivative) is a classic control algorithm used to manage the car's movements, helping it maintain stable control by adjusting outputs based on errors in position, velocity, or other states. **MPC** (Model Predictive Control) is a more advanced control strategy that uses a model of the system's dynamics to predict future states and optimize control inputs over a defined time horizon, often providing better performance in more complex, dynamic environments. **Cyclone DDS** (Data Distribution Service) is a middleware that facilitates the real-time exchange of data between components in a distributed system, and it’s an important tool for ensuring efficient communication in ROS 2-based systems. **DDS** (Data Distribution Service) in general is a standard for middleware communication that is highly scalable and optimized for real-time data exchange, offering reliability and flexibility in handling large amounts of sensor data or messages. Finally, **RViz** is the visualization tool in ROS. It allows for the graphical representation of data from sensors, robot models, and environmental information, providing developers with a clear view of how the robot or simulation is interacting with the world. Understanding these terms is crucial for designing and controlling the QCAR system, as they form the backbone of its decision-making and real-time data processing.

## Results

In terms of actual connectivity, the interaction between the programmer’s machine and the car is built around a clear and well-defined communication protocol. The car itself runs **Ubuntu Linux**, which is a key part of the system architecture. Ubuntu is often chosen for robotics and simulation environments because it is stable, open-source, and has a strong developer community. Its robust package management system, ease of integration with various tools (like ROS, Gazebo, and others), and widespread support in the robotics world make it an ideal choice. By using Ubuntu, we’re also ensuring compatibility with the broader Linux ecosystem, which is crucial for handling the low-level drivers, system dependencies, and the underlying network communication needed to interface with the car.

Since the virtual environment is essentially going to be a **digital twin** of the car, it is vital to mirror the car's operating system in the virtual space. Ubuntu Linux is a perfect fit for this, as it simplifies deployment and ensures that the simulation environment is as close to the real-world environment as possible. Additionally, Ubuntu's performance optimization and flexibility make it a natural choice for running resource-intensive simulations like Gazebo.

When it comes to middleware, **ROS** is unavoidable in this situation. ROS (Robot Operating System) acts as the communication layer that binds all the components together. Without ROS, integrating the different subsystems, from the car's sensors to the programmer's commands, would be exceedingly complex. ROS handles the message-passing, synchronization, and data sharing between various modules in the system. There’s also the option of **ROS 2**, which is a newer version of ROS with improvements like real-time communication, better security, and enhanced performance. However, after evaluating the two, **ROS** is likely the best fit for this project, mainly because it’s widely used and has a larger pool of resources, libraries, and documentation available. ROS 2 has some advantages, but it’s not yet as mature or widely adopted in the same way ROS is, especially when it comes to the integration of third-party tools and legacy systems. So, for the time being, **ROS** remains the go-to option.

One of the strongest aspects of ROS is its seamless integration with **Gazebo**. Gazebo is an open-source simulation tool that can be easily coupled with ROS, allowing for realistic physical simulation of robots and their environments. The integration is so well-established that it’s almost a default in many robotics projects. Gazebo handles the physics simulation, while ROS handles the control, sensing, and high-level logic, making them a perfect pair. Given the need for a high-fidelity simulation of the car and its environment, **Gazebo** will definitely be used in this setup.

On the control side, the **high-level control logic** is what we will primarily be interacting with. This is the “mind” of the robot, where the actual decision-making and planning happen. In this case, **Python** will be the language used to handle the control logic. Python is not only easy to work with but also has extensive libraries for interacting with ROS, Gazebo, and other tools in the ecosystem. It acts as an abstraction layer over ROS, which means that as developers, we won’t need to dive deep into ROS’s lower-level messaging system. However, we will still need to have a foundational understanding of how ROS works, as we will likely have to interact with its nodes and topics at some point. But Python will act as our interface, simplifying the complexity of direct communication with ROS.
